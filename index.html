Le Bouclier Statique - Le Principe Central de l'Architecture

✅ Notre Architecture
  • 1M visiteurs lisent rankings.json depuis Cloudflare CDN
  • 0 requête à la base de données
  • $0 de coût supplémentaire
  • Cloudflare absorbe le trafic gratuitement et sans limite
  • CRON toutes les 5 min : BDD → Agrégation → JSON → CDN
❌ Architecture Classique
  • 1M visiteurs = 1M requêtes à la BDD
  • Risque d'effondrement sous la charge
  • ~$300 juste pour les lectures
  • Besoin d'un serveur surdimensionné
  • Latence élevée pour chaque visiteur
⚙️ 3 prérequis de configuration Cloudflare (sans eux, le Bouclier ne fonctionne pas) :
1. Origine du fichier : le CDN Cloudflare est un cache, pas un stockage - on ne peut pas y "pousser" un fichier. Le CRON dépose rankings.json sur Cloudflare R2 (gratuit à ce volume, egress $0) exposé via le domaine custom data.goldenpala.com.
2. Cache Rule JSON : Cloudflare ne met pas les fichiers .json en cache par défaut. Une Cache Rule explicite est requise : Cache Everything sur /rankings*.json avec Edge TTL de 5 minutes (aligné sur le CRON).
3. Cache HTML WordPress : pour tenir 1M de visiteurs sur l'hébergement OVH Performance, les pages HTML de WordPress sont aussi cachées (Cache Rule Cache Everything sur les pages publiques, purge via plugin Cloudflare à chaque mise à jour de contenu). La règle est couplée à des règles Bypass sur /wp-admin*, /wp-login.php et toute requête portant un cookie wordpress_logged_in_* (disponible sur le plan Free) - sans quoi la session admin casse, ou pire, une page authentifiée serait mise en cache public.

À la clôture du vote, un sceau numérique SHA-256 est calculé sur l'ensemble des votes. Sa propriété : si un seul vote est modifié après coup, le hash recalculé ne correspond plus.

Le sceau ne vaut que s'il est déposé hors de nos mains. Un hash que seul l'opérateur détient ne prouve rien - celui qui contrôle la base pourrait le recalculer. Immédiatement après le gel, le hash est donc : (1) consigné dans le procès-verbal du commissaire de justice, et (2) publié publiquement sur la page de résultats de goldenpala.com, horodaté, ainsi que dans le bulletin diffusé. Une fois le sceau entre les mains de tiers, plus personne - équipe technique incluse - ne peut altérer un vote sans que la fraude soit détectable par simple recalcul. La garantie ne repose pas sur la confiance envers l'opérateur, mais sur la publication.

Périmètre exact : le sceau garantit l'intégrité des votes après la clôture. L'intégrité pendant la fenêtre de vote repose sur les contraintes de base de données, le pipeline de validation et l'audit trail immuable (voir Sécurité et Schéma de Données).

Le problème : par défaut, les votes partent du navigateur directement vers xxxx.supabase.co. Ce trafic ne transite pas par notre zone Cloudflare - nos règles de protection Edge ne le voient donc pas, et chaque requête qui atteint Supabase compte comme une invocation facturable ($2 par million au-delà de 2M). Un flood massif serait bloqué par le pipeline applicatif (0 email envoyé), mais après le compteur d'invocations.

La solution : l'add-on Custom Domain de Supabase ($10/mois) expose l'API sur api.goldenpala.com, derrière notre propre proxy Cloudflare. Les protections Edge s'appliquent alors avant toute facturation : une requête bloquée par Cloudflare ne touche jamais Supabase - $0.

Pourquoi pas un challenge interactif (Managed Challenge) ? Une réponse challenge ne peut pas être résolue dans un appel fetch() - elle casserait silencieusement les votants légitimes (VPN, navigateurs privés). La preuve « vrai navigateur » est déjà portée par Turnstile, dans le formulaire, là où l'interaction est possible.

Tables Principales

Pourquoi cette table existe : les votes ne pointent pas directement vers joueurs, car un "nominé" n'est pas toujours un joueur unique. La table nomines sépare être une personne de être candidat dans une catégorie :

CatégorieOn vote pour…Représentation dans nomines
GOLDEN PALAUn joueur1 ligne, type joueur, joueur1_id
GOLDEN PAREJAUne paire1 ligne, type paire, joueur1_id + joueur2_id
GOLDEN PROMESAUn joueur < 21 ans1 ligne, type joueur - un même joueur peut être nominé dans 2 catégories (2 lignes)
GOLDEN PROFESORUn coach1 ligne, type coach (pas de classement FIP requis)

Sans cette table, il serait impossible de voter pour une paire (un nomine_id ne peut pas désigner deux joueurs) ou de nominer un jeune joueur à la fois en PALA et en PROMESA.

Contraintes Clés

  • nomine_id - FK vers nomines (jamais vers joueurs directement)
  • UNIQUE (voter_type, voter_id, award_category) - 1 vote par collège par catégorie
  • UPSERT - Le vote peut être changé, le dernier vote écrase le précédent
  • is_invalidated - L'admin peut invalider un vote frauduleux sans le supprimer
  • email_hash - HMAC-SHA256 de l'email normalisé (minuscules, alias Gmail neutralisés - ADR-007) avec secret serveur (pepper) : pseudonymisation RGPD, résistante aux attaques par dictionnaire (votes publics)

Index de Performance

-- Recherche rapide des votes par catégorie (agrégation)
CREATE INDEX idx_vip_votes_category ON vip_votes(award_category) WHERE is_invalidated = FALSE;
CREATE INDEX idx_public_votes_category ON public_votes(award_category) WHERE is_invalidated = FALSE;

Cette table est append-only par construction : aucun rôle applicatif (admin inclus) ne peut modifier ou supprimer une entrée - droits révoqués et trigger de blocage. Honnêteté technique : comme dans toute base de données, un superutilisateur du projet pourrait théoriquement contourner ces verrous. C'est pourquoi la garantie légale n'est pas technique mais cryptographique : le hash SHA-256 de clôture (ADR-005), remis au commissaire de justice et publié publiquement, rend toute altération a posteriori détectable - y compris par l'opérateur lui-même.

-- Sécuriser l'immuabilité
ALTER TABLE admin_audit_logs ENABLE ROW LEVEL SECURITY;
REVOKE UPDATE, DELETE ON admin_audit_logs FROM PUBLIC;
REVOKE UPDATE, DELETE ON admin_audit_logs FROM authenticated;

-- Verrou supplémentaire : bloque aussi service_role et les erreurs d'admin
CREATE FUNCTION forbid_audit_mutation() RETURNS trigger AS $$
BEGIN RAISE EXCEPTION 'admin_audit_logs is append-only'; END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER audit_append_only
BEFORE UPDATE OR DELETE ON admin_audit_logs
FOR EACH ROW EXECUTE FUNCTION forbid_audit_mutation();

Les codes OTP sont hashés en HMAC-SHA256 avec un secret serveur (pepper) avant stockage - le code brut n'est jamais conservé en base. Le pepper est indispensable : un code à 6 chiffres n'a que 1 million de combinaisons, un simple SHA-256 non salé se brute-forcerait en quelques millisecondes en cas de fuite de la table.

  • status : PENDING → USED ou EXPIRED
  • attempts : Max 3 tentatives avant invalidation
  • expires_at : Validité de 10 minutes
  • ip_hash : HMAC-SHA256 de l'IP du demandeur (jamais l'IP en clair - c'est une donnée personnelle RGPD). Sert uniquement au fusible "30 OTP / IP / heure"
  • created_at : horodatage servant de base à toutes les fenêtres de comptage (index sur (ip_hash, created_at) et (email, created_at))
  • Purge automatique : les lignes de plus de 24h sont supprimées par pg_cron - elles ne servent qu'au rate limiting, on ne conserve rien au-delà

Alimentée par les notifications SNS d'AWS SES (bounces et plaintes), consultée par le pipeline avant tout envoi. Son rôle : empêcher le taux de bounce de grimper - un taux élevé ferait suspendre le compte SES en pleine période de vote.

La suppression a une durée de vie (TTL) différenciée par cause - pour qu'une adresse créée après avoir été saisie par erreur ne soit jamais bloquée définitivement :

⚠️ Double niveau de suppression :
AWS SES maintient sa propre liste de suppression au niveau du compte, alimentée automatiquement par les hard bounces. Lever une suppression se fait donc aux deux endroits : notre table + l'API SES (DeleteSuppressedDestination). L'admin dispose d'une procédure de déblocage manuel (tracée dans l'audit log) pour tout votant légitime qui contacte le support - personne n'est exclu définitivement par une machine.

Table clé/valeur qui porte l'état interrogeable du système - l'audit log enregistre les événements, mais un log n'est pas un état. Toutes les Edge Functions, le CRON et le script de gel lisent cette table :

  • vote_ouverture / vote_cloture - les bornes de la fenêtre de vote (source de vérité unique, pas de dates codées en dur)
  • vote_gele - le flag posé par le script de gel : dès qu'il est true, toute écriture de vote est refusée
  • turnstile_actif - switch anti-bot : si le quota gratuit Turnstile (1M vérifications/mois) approche en phase virale, une requête SQL bascule le formulaire sur ALTCHA (auto-hébergé, illimité, $0) sans déploiement - voir Scalabilité
  • hash_cloture - le sceau SHA-256 final : c'est ici que le commissaire de justice le retrouve, en plus de l'audit log et de la page publique de résultats où il est publié à la clôture (ADR-005)
Intégrations

Intégrations Tierces

Le système s'interface avec 5 services externes. Chaque intégration est documentée avec son rôle, son coût, et les données échangées.

🛡️ 1. Cloudflare Turnstile (Anti-Bot Applicatif)

Objectif : Remplacer Google reCAPTCHA pour protéger le système de vote public contre le spam automatisé et les attaques DDoS de niveau applicatif, sans frustrer l'utilisateur légitime avec des grilles d'images à résoudre.

Vérifiabilité & Conformité :
Turnstile est nativement conforme au RGPD. Contrairement à reCAPTCHA, il ne dépose pas de cookies de tracking inter-sites. Le plan gratuit inclut 1 million de vérifications serveur (siteverify) par mois - largement suffisant jusqu'à ~1M de votants, car l'architecture ne consomme qu'une seule vérification par demande d'OTP (les actions suivantes sont couvertes par le JWT, sans re-vérification). Au-delà du million, Cloudflare n'interrompt pas le service mais oriente vers un plan Enterprise - voir la mitigation en section Scalabilité.

Flux Technique & API

  • Le widget client génère un token cryptographique temporaire nommé cf-turnstile-response.
  • Le backend (Edge Function Supabase) intercepte la soumission du vote et bloque l'insertion en base de données.
  • L'Edge Function vérifie la validité du token via une requête POST vers https://challenges.cloudflare.com/turnstile/v0/siteverify en utilisant la clé secrète serveur (stockée dans le Vault Supabase).
  • L'opération d'écriture n'est autorisée que si le score de confiance renvoyé est validé.

📧 2. Resend → bascule vers AWS SES (Emails Transactionnels)

Objectif : Garantir l'envoi immédiat (< 2 secondes côté serveur ; réception typique < 30 s, dépendante de la messagerie du destinataire - greylisting Gmail/Outlook) des codes OTP à 6 chiffres pour le grand public, et des Magic Links pour l'authentification des journalistes et légendes.

Vérifiabilité des Coûts (Important) :
Le tier gratuit de Resend bloque à 100 emails/jour (3000/mois). Pour encaisser 1 million de votes en 15 jours, l'architecture bascule sur l'API HTTP d'AWS SES (SES v2 SendEmail). Le coût officiel d'AWS SES est d'exactement 0.10$ pour 1000 emails - soit $100 pour 1 million d'emails envoyés. Le budget est provisionné sur une base de ~2 emails par votant (redemandes de code, renvois, magic links) : ~$200 pour 1M de votants, ~$1 000 pour 5M. Cette hypothèse est appliquée uniformément dans toutes les projections de ce document.

Flux Technique & API

  • L'envoi est déclenché par l'Edge Function (Supabase Auth n'est pas utilisé pour les votants - voir Sécurité) via API HTTP, à travers une interface d'envoi unique (sendEmail()). Le SMTP est volontairement écarté : en serverless, il coûterait une poignée de main TCP/TLS par invocation - l'appel HTTP est plus rapide et plus fiable.
  • Resend (POST https://api.resend.com/emails, clé API) et SES v2 (SendEmail, signature SigV4) sont deux adaptateurs derrière la même interface : la bascule en production = EMAIL_PROVIDER=ses, sans récrire une seule ligne de code métier.
  • Prérequis SES anticipés : accès production + augmentation de quota demandés 2 semaines avant l'ouverture (voir ADR-002).

🌐 3. WordPress API REST (Synchronisation Headless)

Objectif : Conserver une séparation stricte entre le front-end (WordPress) et la base de données sécurisée (Supabase), tout en gardant les deux systèmes synchronisés automatiquement.

Migration de Webflow vers WordPress :
L'interface actuelle sur Webflow sera migrée vers WordPress hébergé sur OVH.
Plan de migration :
1. Export statique du design Webflow (HTML/CSS/JS).
2. Intégration sur-mesure dans WordPress (Thème ultra-léger, sans constructeur type Elementor pour garantir des temps de chargement < 1s).
3. Mappage des Custom Post Types pour que l'admin puisse éditer les joueurs et catégories depuis l'interface WordPress familière.

Flux Technique & API

  • Lorsqu'un profil de nominé est mis à jour dans Supabase, un Database Trigger (déclencheur SQL) est exécuté.
  • Ce trigger invoque une fonction asynchrone qui appelle l'API REST native de WordPress (POST /wp-json/wp/v2/nomines) en s'authentifiant avec un Application Password.
  • Le site WordPress est mis à jour en temps réel.
  • Diffusion des classements (Haute Charge) : Pour afficher le classement sans faire exploser l'API du CMS ni la base de données, le CRON Supabase génère toutes les 5 minutes un fichier statique rankings.json, déposé sur Cloudflare R2 (origine) et servi par le CDN via une Cache Rule dédiée (voir section Architecture). Le front-end WordPress vient lire ce fichier léger en JavaScript natif, permettant d'encaisser des millions de visiteurs simultanés.

📰 4. Brevo → bascule vers Sendy (CRM Marketing)

Objectif : Gérer la liste d'attente ("Notify Me"), annoncer l'ouverture des votes et promouvoir les résultats finaux, tout en isolant complètement ce flux du moteur d'OTP pour protéger la réputation IP du domaine de vote.

Vérifiabilité des Coûts (Important) :
Mailchimp ou Brevo (en payant) coûtent extrêmement cher pour des envois massifs à 100 000+ contacts (plusieurs centaines de dollars par mois). La solution d'architecture propose le duo Sendy + AWS SES. Sendy est un logiciel à licence unique de $69 (pas d'abonnement) qui s'auto-héberge en PHP/MySQL - soit directement sur l'hébergement OVH Performance déjà acquis ($0 de plus), soit sur une petite instance EC2 (~$5/mois). Il envoie via SES, faisant chuter le coût de la newsletter à environ 1$ pour 10 000 envois.

Flux Technique & API

  • Pendant le MVP : Le formulaire de capture WordPress (via plugin léger) est directement connecté au endpoint POST /v3/contacts de Brevo. Brevo permet le stockage gratuit illimité de contacts.
  • Lors du passage à l'échelle (Phase 2) : L'API Sendy (script PHP REST) prend le relais pour l'envoi massif sans surcoût de licence mensuelle.

🏆 5. Padel Data Provider (Alimentation Télémétrie)

Objectif : Alimenter de manière autonome la table TELEMETRIE_CLASSEMENT du système avec les classements officiels FIP / Premier Padel des joueurs nominés.

Performance :
Ce processus s'exécute en tâche de fond (background worker), il n'y a donc aucun impact sur le temps de chargement des pages pour les visiteurs (latence perçue = 0).

Limites du plan gratuit : 50 000 requêtes/mois avec accès aux classements actuels - très largement suffisant pour une synchronisation hebdomadaire d'une centaine de nominés. ⚠️ L'historique complet des saisons passées est réservé aux plans payants : si le client souhaite afficher l'évolution pluriannuelle des joueurs, ce coût sera chiffré séparément.

Flux Technique & API

  • Configuration de l'extension native PostgreSQL pg_cron dans Supabase.
  • Un worker est planifié pour s'exécuter tous les lundis à 02:00 AM UTC (heure de mise à jour standard des classements ATP/FIP).
  • Le worker fait une requête GET authentifiée vers l'API externe, parse le JSON reçu, et exécute une opération UPSERT de type bulk dans la base PostgreSQL pour mettre à jour l'évolution des joueurs nominés.

Protocoles de Sécurité

Chaque couche de l'architecture est sécurisée indépendamment. La fraude est rendue économiquement coûteuse sans dégrader l'expérience du votant légitime.

Défense en Couches - Chaque Fusible Devant Son Compteur

Le principe directeur : chaque couche bloque l'abus avant la ressource qu'elle protège. Il y a trois "compteurs" qui coûtent de l'argent (les invocations Edge Functions, les emails envoyés, l'intégrité du vote) - et un fusible placé devant chacun. La sécurité de l'identité repose sur l'email + OTP ; l'IP n'est jamais utilisée pour identifier un votant (tolérance totale aux wifi partagés, 4G/CGNAT, clubs de padel).

  1. Couche 1 - Cloudflare Edge (devant le compteur d'invocations) : avec le Custom Domain api.goldenpala.com (voir ADR-006, recommandé), une règle WAF (Block) rejette au bord du réseau tout POST vers la route OTP dont l'Origin n'est pas le site officiel (élimine les scripts naïfs), et une règle de rate limiting (Block) coupe les rafales (10 req / 10 s / IP). Pas de challenge interactif sur un endpoint API : une réponse challenge ne peut pas être résolue dans un fetch() - la preuve « vrai navigateur » est le rôle de Turnstile (couche 2). Requête bloquée ici = $0 facturé. Sans Custom Domain, cette couche n'existe pas et le pire cas d'un flood est borné à ~$100 d'invocations.
  2. Couche 2 - Cloudflare Turnstile (Comportemental) : challenge invisible vérifié côté serveur dans l'Edge Function, bloquant 99% des bots restants sans pénaliser les IP partagées. Fonctionne quel que soit le routage (la vérification siteverify est serveur-à-serveur).
  3. Couche 3 - Pipeline applicatif (devant le compteur d'emails) : une requête qui atteint la fonction traverse, dans l'ordre : validation syntaxique de l'email → blocklist des domaines jetables → vérification MX du domaine → quota IP (fusible) → quota email. Aucun email n'est envoyé tant que tout n'est pas vert. Détail ci-dessous.
  4. Bypasse de Supabase Auth (Stratégie de Coût) : Décision majeure. Nous n'utiliserons pas le module natif "Supabase Auth" pour les votants. Au-delà de 100 000 MAU inclus, Supabase facture 0.00325$ par votant : pour 5 millions de votants, cela coûterait ~15 925$. En gérant nous-mêmes les OTP de manière "stateless" dans une table dédiée via Edge Functions, le coût serveur reste bloqué à 25$/mois !

Pipeline de Validation Email - la Route /request-otp

On ne peut pas savoir à l'avance qu'une adresse email existe (les serveurs mail mentent volontairement aux sondes) - et on n'en a pas besoin : l'OTP est lui-même le test d'existence. Les filtres en amont servent uniquement à ne jamais payer un email inutile et à protéger la réputation d'expéditeur :

1
Vérification Turnstile
Le token cf-turnstile-response est validé côté serveur. Échec → réponse 200 silencieuse.
2
Syntaxe + Blocklist temp-mail + Liste de suppression
Regex de format, normalisation de l'adresse (minuscules ; pour Gmail : suppression des points et du suffixe +tag - ferme le vote multiple par alias, voir ADR-007), rejet des domaines jetables (yopmail, mailinator… - liste open-source de ~4 000 domaines embarquée dans la fonction), puis vérification de la table emails_supprimes (adresses ayant bouncé - suppression à durée de vie, voir Schéma de Données).
3
Vérification MX du domaine
Deno.resolveDns(domaine, "MX") (~20 ms) : le domaine peut-il recevoir des emails ? Élimine tous les domaines inventés sans coûter un envoi. Fallback prévu si l'API DNS n'est pas disponible dans le runtime Supabase : requête DoH vers cloudflare-dns.com/dns-query?type=MX (simple fetch(), même latence, même résultat).
4
Fusible IP (30 / heure) puis quota email (3 / 24h)
Comptage en base sur otp_codes (voir ci-dessous). Dépassé → 200 silencieux, pas d'email.
5
Envoi de l'OTP
Seule une requête qui a passé toutes les étapes coûte un email. Les bounces SES (via notifications SNS) alimentent une liste de suppression : une adresse qui a rebondi ne recevra plus jamais d'envoi - protection de la réputation d'expéditeur.

Rate Limiting Applicatif (Edge Functions)

RègleLimiteAction si dépassée
OTP demandés par IP / heure Max 30 Réponse 200 silencieuse (pas d'email envoyé)
OTP demandés par email / 24h Max 3 Idem - réponse identique au succès
Tentatives OTP incorrectes Max 3 OTP invalidé, blocage 15 minutes
Votes par email_hash / catégorie Max 1 UPSERT - le nouveau vote remplace l'ancien
💡
Pourquoi répondre 200 même en cas de blocage ? Si on répond 429, un bot peut tester des milliers d'emails et savoir lesquels ont déjà voté (énumération). En répondant toujours 200, le bot ne sait jamais s'il a réussi.
🔌
Pourquoi 30/heure par IP et pas 5 ? La limite IP est un fusible économique, pas une serrure d'identité : l'unicité du vote est garantie par l'email (contrainte UNIQUE sur email_hash), jamais par l'IP. Le seuil est donc volontairement large pour qu'un club de padel entier votant derrière le même wifi, ou un réseau 4G en CGNAT, ne soit jamais gêné - un humain n'atteint jamais 30 demandes/heure, un script d'attaque crève le seuil en quelques secondes. Comme tout header HTTP, l'IP transmise est du best effort : c'est acceptable pour un fusible, et c'est pour cela que ce n'est pas la couche qui porte l'identité.

Couches de Sécurité en Profondeur

🔒 Row Level Security (RLS)
Chaque ligne de la BDD a sa propre "serrure". Même si quelqu'un pirate la connexion, il ne peut lire que les données autorisées. Les audit logs sont en lecture seule pour tout le monde.
🔑 JWT Signé (HMAC-SHA256)
Chaque session est un badge électronique signé cryptographiquement. Impossible de le falsifier ou de modifier le contenu (voter_type, voter_id) sans invalider la signature.
🧊 OTP Hashé (HMAC-SHA256 + pepper)
Le code OTP n'est jamais stocké en clair en base. Seul le hash HMAC-SHA256, calculé avec un secret serveur (pepper) stocké hors BDD, est conservé. Même en cas de fuite de la BDD, les codes sont inutilisables.
📋 Audit Trail Immuable
Chaque action admin est enregistrée dans un journal qu'on ne peut ni modifier ni supprimer (REVOKE UPDATE, DELETE). Preuve légale pour le commissaire de justice.

Sécurisation du Frontend WordPress

WordPress est la brique la plus exposée de la stack - c'est le CMS le plus attaqué du web. L'architecture le cantonne donc à un rôle de vitrine : il ne détient aucun secret (tout est dans le Vault Supabase), ne touche jamais aux votes, et toute la logique sensible vit dans les Edge Functions. Une compromission de WordPress serait un incident d'image, pas un incident de données. Il est néanmoins durci :

MesureDétail
2FA sur tous les comptes admin Obligatoire sur wp-admin (plugin 2FA dédié). Comptes limités au strict nécessaire : rôle Éditeur pour le client, Administrateur pour le développeur uniquement.
Protection de wp-login.php Règle WAF Cloudflare Managed Challenge sur la page de login - contrairement à l'API de vote (ADR-006), un challenge interactif est ici possible (page chargée dans un navigateur), et il neutralise le brute force sans consommer la règle de rate limiting du plan Free (unique, déjà allouée à la route OTP).

Édition de fichiers désactivée DISALLOW_FILE_EDIT dans wp-config.php : même un compte admin compromis ne peut pas injecter de code PHP depuis le dashboard.

🛡️
Rayon d'impact borné : même en cas de défacement de la vitrine WordPress, les votes, les classements et l'intégrité du scrutin restent intacts - ils vivent dans Supabase, derrière une API séparée, et rankings.json est servi depuis R2. Le pire scénario WordPress est une page d'accueil vandalisée pendant le temps de la restauration (< 1h avec le runbook), pas une altération du vote.

Structurel, prévisible
2. Invocations en cas de flood
Une attaque massive sur l'API consomme des invocations à $2/M - pire cas borné à ~$100. Avec le Custom Domain + règles WAF/rate limiting (ADR-006), les attaques courantes sont bloquées avant la facturation (~$0) ; un flood distribué sophistiqué reste borné à ~$100, la mitigation DDoS L7 automatique de Cloudflare en dernier rempart.
Borné, mitigé
3. Egress si cache mal configuré
Si la Cache Rule de rankings.json était oubliée, 1M de visiteurs liraient Supabase en direct : ~250 Go d'egress dépassés puis $0.09/Go. C'est un risque de configuration, éliminé par la checklist de pré-lancement (item 5) et les alertes de facturation.

Fusible IP - Implémentation de Référence

La règle "30 OTP / IP / heure" s'implémente entièrement dans l'Edge Function - rien à configurer côté infra. L'état vit dans la table otp_codes (la fonction est stateless, la base ne l'est pas) :

Edge Function - request-otp/index.ts (extrait)
// 1. LIRE l'IP - méthode documentée Supabase : premier élément de x-forwarded-for
const ip = req.headers.get("x-forwarded-for")?.split(",")[0]?.trim() ?? "inconnue";

// 2. HASHER - RGPD : l'IP est une donnée personnelle, jamais stockée en clair
const ipHash = await hmacSha256(ip, Deno.env.get("OTP_PEPPER")!);

// 3. COMPTER - la "règle" est ce simple SELECT (index sur (ip_hash, created_at) : ~2 ms)
const { count } = await sql`
  SELECT count(*) FROM otp_codes
  WHERE ip_hash = ${ipHash}
    AND created_at > now() - interval '1 hour'`;

if (count >= 30) {
  // Réponse identique au succès : anti-énumération
  return json({ ok: true }, 200);
}
// ...suite du pipeline : quota email (3/24h), insertion, envoi de l'OTP
💡
Deux détails d'implémentation : (1) le header x-forwarded-for est la méthode supportée par Supabase pour obtenir l'IP du client dans une Edge Function ; (2) deux requêtes strictement simultanées peuvent théoriquement passer le comptage toutes les deux (31ᵉ demande au lieu de 30) - acceptable pour un fusible économique, ce n'est pas un compteur comptable.

Règles Métier - Cas Limites de l'Agrégation

Collège sans vote
Si un collège n'a émis aucun vote dans une catégorie (division par zéro dans la normalisation), son poids est redistribué proportionnellement aux collèges restants (ex: 0 vote Légendes → Journalistes 50/70, Public 20/70).
Égalité parfaite
En cas de score final identique entre deux nominés, le départage se fait par le % du collège Journalistes (collège au poids le plus fort), puis Légendes, puis Public.
Arrondis
Les scores sont calculés en numeric(10,4) (4 décimales) côté SQL et arrondis uniquement à l'affichage (2 décimales). Aucun arrondi intermédiaire - sinon les totaux ne font plus 100%.
CORS
Les Edge Functions n'acceptent que l'origine https://goldenpala.com (et le staging). Toute autre origine est rejetée - un site tiers ne peut pas appeler l'API de vote depuis un navigateur.
